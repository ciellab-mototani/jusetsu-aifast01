# AI制作サイトの整備・公開ルール

更新：2026-11-04。今回の最終仕様と対応履歴を基にした、次回案件向けの標準。案件固有のドメイン・メール・キーは必ず差し替える。

## 1. 受領時に確認すること

- 元ファイルをGitなどで保存し、変更前の表示・アニメーションを記録する。
- 全ページ、使用技術、画像・CSS・JSの参照、既存フォームの実送信有無を調査する。
- 本番URL、テストURLと設置階層、サーバー・PHP環境、管理者通知先、送信元、SMTP情報、Turnstile、GA4／GTMを確認する。
- 秘密キー・SMTPパスワードはチャットやGitへ載せず、保護した設定ファイルへ入力する。
- 自動返信の要否、文面、通知先を先に確定する。既存SEOや計測タグをそのまま正しいと判断しない。

## 2. ファイル構成

```text
案件フォルダ/
├── *.html                 公開ページ
├── img/                   画像
├── css/                   スタイル
├── js/                    JavaScript
├── contact.php            フォーム受付
├── server/                メール処理・ライブラリ・設定
│   ├── .htaccess          直接アクセス拒否
│   ├── contact-config.php 秘密設定・メール宛先（Git対象外）
│   └── mail-templates.php 管理者通知・自動返信の件名と本文
├── .htaccess              サイトのサーバー設定
├── robots.txt
├── sitemap.xml
└── _アップロード不要/     引き継ぎ・ルール・検証・作業資料
```

- HTMLは第一階層、画像・CSS・JSは種類別にまとめる。必要なPHPと管理ファイルは追加する。
- FTPでは案件フォルダの中身を配置する。_アップロード不要、.git、.gitignore、OS管理ファイルは転送しない。
- ルートとserverの.htaccess、入力済みcontact-config.phpは必ず転送する。隠しファイルの転送漏れを確認する。
- 秘密設定はサイトから直接取得できないよう、.htaccessとPHPの実行ガードで保護する。秘密入りのフォルダ・ZIPは共有しない。
- 管理データはPHPが公開領域外に作成する。作成権限がない場合、公開領域へ逃がさず権限を調査する。
- フォルダ整理時は検証スクリプトや手順書の参照先も更新する。

## 3. 見た目・アニメーションを維持する

- 構造整理では移動とパス修正を基本とし、CSS統合・削除・アニメーション改変を同時に行わない。
- CSSの読み込み順、JSの実行順、class・idを維持する。
- HTMLだけでなくCSSのurl()、JSの動的HTML、正規表現、data属性、アンカーも確認する。
- 同名画像を上書きしない。URL変更は対応表を残し、公開済みURLには必要な転送を設定する。
- PC・スマホの変更前後を同条件で比較する。目安は1280・390・320px、案件に応じてタブレットも追加する。
- 静止画だけでなく動きの開始・途中・終了、スクロール連動、停止・再開、動きを減らす設定を確認する。
- メニュー、FAQ、追従ボタン、フォーム開閉、画像切れ、横はみ出し、JSエラーも確認する。
- 自動比較と実機確認を区別する。未確認の端末について動作保証したと報告しない。

## 4. フォームの標準

- WordPressなしの案件ではPHP＋SMTP認証送信＋Cloudflare Turnstileを基本とする。
- 全ページでフォームと送信処理を共通化する。ボタンに応じて問い合わせ種別・見出し・送信ボタン文言を切り替える。
- サブフォルダ設置でも動く参照パスにする。本番・テストの許可ホストは明示し、任意のHostを信用しない。
- 保守されたSMTPライブラリを使用し、TLS証明書を検証する。ユーザー入力を送信元にしない。
- 管理者通知の宛先・送信元・SMTP認証はcontact-config.phpで管理する。
- 件名・本文はmail-templates.phpへまとめる。段落、項目ごとの改行、空行、控えめな区切り線を使う。
- 自動返信は入力内容の確認と問い合わせ先を載せる。内部の受付IDはメールに表示しない。
- 管理者通知がSMTPに受理された後に自動返信する。自動返信だけの失敗で受付済み問い合わせを失敗扱いにしない。
- SMTPの受付成功と受信箱への到達は別。管理者・ユーザーの両方で実受信を確認する。

## 5. セキュリティ対策と担当箇所

| 対策 | 実装箇所 |
| --- | --- |
| bot対策 | Cloudflare Turnstile＋PHPによる成功・hostname・action・期限の検証 |
| 不正な送信元対策 | PHPのHost・Origin・CSRFトークン等の検証 |
| 不正な入力対策 | PHPの必須項目・形式・文字数・選択肢・本文サイズ・ヘッダー改行の検証 |
| 連続送信制限 | PHP＋非公開SQLiteの回数管理 |
| 二重送信防止 | JSの送信中制御＋PHP／SQLiteの受付状態・内容照合 |
| メール通信保護 | SMTP認証・TLS・証明書検証 |
| 秘密設定保護 | .htaccess、PHP直接実行ガード、Git除外 |
| テスト環境保護 | サーバー側のBasic認証 |

- 認証サービスやDBが失敗したら送信を止める。認証を迂回する復旧はしない。
- SMTPの明確な失敗と結果不明を分け、結果不明時は自動再送しない。
- フォーム内容・パスワード・トークンをログや解析サービスへ送らない。診断ログは段階・例外種別・数値コードなどに限定する。
- Turnstileの許可ホストにはドメインだけを登録する。https://やサブフォルダは含めない。
- Cloudflare Turnstileの導入と、サイト全体のCloudflare WAF／プロキシ導入を混同しない。
- エックスサーバーのWAFは有効状態で正規送信を確認する。無断で全体を無効化しない。
- 本案件の制限はIPごと送信5回／15分、メールごと5回／時間、全体100回／時間。試験も制限対象。値は案件に合わせて判断する。

## 6. SEO・計測

- 各ページに内容に合う固有のtitle・descriptionを設定する。canonical・OGP・favicon・sitemapも本番URLに合わせる。
- 全ページで計測コードを共通化し、HTTPSの本番ホストだけGA4／GTMを読み込む。テストの閲覧・送信は本番計測へ混ぜない。
- GA4直接設置とGTMの併用時は、公開コンテナ内のタグを確認し二重計測を防ぐ。GTM側の変更時も再確認する。
- CTAクリックと問い合わせ受付成功を別イベントにする。成功イベントはPHPの受付成功後に送る。
- 氏名・メール・電話・相談内容をイベントへ含めない。URLパラメーターなどの収集にも注意する。
- 共通ファイルへ無条件のGTM noscript iframeを入れない。本案件ではJavaScript無効時のGTMは非対応とする。
- 本番公開後、GA4の実受信・generate_leadのキーイベント設定・Search Consoleなど管理画面側を確認する。コード確認のみで計測完了とはしない。

## 7. 本番とテストで同じファイルを使う

- HTMLはindex,follow。本番用・テスト用の手動切り替えや別ビルドを標準にしない。
- テストサイトはアップロード前にサーバー側で全体へBasic認証を設定する。
- Basic認証はサイトの親フォルダで設定し、FTPでサイトの.htaccessを更新しても認証設定を消さない構成にする。
- アクセス制限ONだけでなく認証ユーザーを登録する。AuthUserFileが指す.htpasswdの存在と、ログイン前は見られずログイン後に見られることを確認する。
- 本番ではBasic認証や以前のX-Robots-Tag: noindexが残っていないことを確認する。
- サイトを変更するたび、テスト用のメール宛先が残っていないか確認する。本番へ戻した設定ファイルも再アップロードする。
- 既存サーバーの設定・ファイルをバックアップし、復元手順を決めてから公開する。

## 8. テストの範囲

| 確認 | 範囲 |
| --- | --- |
| フォームが開く・初期種別が正しい | 全ページの各問い合わせボタン。送信不要 |
| 認証・受付・両方のメール受信 | トライアル・資料請求・問い合わせを各1回 |
| 入力内容・種別・改行・宛先 | 上記の受信メールで確認 |
| 必須・メール形式・同意のチェック | 共通フォームで代表確認 |
| スマホ | 開閉・スクロール・認証・送信。実送信の1回をスマホに割り当てる |
| 不正入力・期限切れ・制限・二重送信・障害 | スタブ等を用いた自動テストで確認 |
| 本番 | HTTPS・転送・検索設定・計測・フォーム実受信を最終確認 |

全ボタンから実メールを送る必要はない。ローカルの外部通信を置換した試験、実サーバーの認証、メール実受信、実機表示を分けて記録する。

## 9. 今回のつまずきと次回の予防

| 内容 | 次回のルール |
| --- | --- |
| 画像移動でJSの許可パターンと不一致 | パス文字列だけでなく正規表現とアニメーション後の表示も確認 |
| ファイルが分散し作業資料も混在 | 公開ファイルはルート中心、作業資料は_アップロード不要に集約 |
| 公開URLにpublic_htmlを含めるか混乱 | FTP配置先とブラウザURLを別々に示す。public_htmlは通常URLに含めない |
| フォーム初期化がPDOExceptionで停止 | サーバーのSQLite環境を確認。古いSQLiteでも動くSQLを使い、数値コードで診断できるログを用意。今回の詳細原因はログだけでは断定していない |
| 自動返信の要否・文面を後から調整 | 管理者通知と自動返信を着手前に確認。入力内容の控えと読みやすい改行を標準化 |
| テスト宛先の変更とFTP反映が分かりにくい | 変更ファイルと配置先を毎回明示。SMTP受付と到達を区別して調査 |
| 本番・テストの切り替えが煩雑 | 同じファイル＋本番ホストのみ計測＋テスト側Basic認証に統一 |
| Basic認証ON後に500、認証ファイルなし | ユーザー登録と.htpasswd作成をセットで確認。今回はユーザー側の設定後に表示復旧 |
| 関係のないログで調査が進まない | 再現時刻・対象パスの一致を確認し、秘密を含むファイル全体を求めない |

## 10. 記録と報告

- 「問題／原因（確定か推定か）／対応／検証結果／次回の予防／所要時間」を記録する。
- 所要時間は実測だけを書く。今回の工程別時間は未計測であり、推定を実績として記録しない。
- 納品報告にはSEO設定、フォーム、タグ、対策内容、確認済み範囲、公開後に残る確認を簡潔に記載する。
- 「セキュリティ対策済み」を無事故の保証として使わない。実装済みの具体的な対策を説明する。
- 今回はユーザーよりフォーム試験完了・Basic認証後の表示復旧の報告あり。本番公開後の計測受信確認は別工程。
